# 首轮取证共性审计与两个仓库复测

代码版本：`83f00ed`。本轮读取旧全量报告中“没有 Worker 目标位置正式候选”的 12 例日志，随后只修改通用取证及首次审查提示，固定两个仓库做正反四例。没有新增 scanner 规则、探针、仓库特例或修改标签。

## “没有候选”并不总是“没有想到”

这里的候选指结构化 `findings[]`，不是 Worker 的 `hypotheses[]`。多例已经在假设中描述了目标风险，但没有补齐证据或输出正式 Finding。主因不止一个：

| 旧漏检例 | 日志中的主要断点 |
| --- | --- |
| Manim | 已想到属性不存在；预读却从注释抽到 `Where`，转去读压缩 JS，没有读初始化定义。 |
| Calibre | 正确性 Worker 最终没有可追踪结论；跨文件预读跑到无关崩溃报告，安全 Worker 偏到路径穿越。 |
| Sphinx | 已指出不支持哈希的注解会导致异常；未完成相关调用／测试核查，预读还被语言关键词带偏。 |
| Bluetooth | 两个 Worker 对格式占位符数量结论相反，跨域风险没变成正式结论；属于推理与结论转交问题。 |
| Urwid | 对递归结果非空作过强归纳，没有正确处理嵌套空列表；不能只靠改善检索解决。 |
| PyRecest | 已描述显式 dim 被 None 覆盖的差分，但仍停在确认输入契约／意图。 |

| YTMusic | 形成了附近的缺长度检查 Finding，但目标是标签顺序／类型映射错误，不能把相邻缺陷当作目标发现。 |
| Satpy | 已怀疑空过滤列表改变行为，仍未完成数组行为与既有测试契约核查。 |
| Press | 已看到参数默认 None 和迭代 None 的失败，却继续要求额外调用方证明，没有形成 Finding。 |
| Tracecat | 搜索已找到测试调用，预读却停在 import；尚未追到表达式结果的实际消费者／序列化契约。 |
| Collective FAQ | 搜索已找到同文件 `_questions` 定义，预读逻辑却排除了同文件命中，转去读无关 adapter。 |

因此，本轮修复针对的是“证据已可定位但没有送到需要它的模型”这一共性，不宣称能消除递归推理错误或所有输出协议遗漏。

## 小范围修复

- 通过 token 化从不完整代码片段提取标识符，过滤注释、字符串、Python 关键词和内置名称；不依赖整份文件 AST 成功解析，避免新语法令整个文件不可检索。
- 搜索增加可选 `context_path` 排序和 `identifier` 精确匹配。前者优先当前文件／目录，不限制检索范围；后者区分大小写和标识符边界，避免把 `fileName` 混成所有 `filenames`。
- 预读不再排除同文件定义，优先实际定义／调用，允许读到测试断言；不再把 import 或词语偶遇当作下一跳目标。
- 维持最多两次初始搜索和一次依赖正文读取，删除无关第二跳扩散。已有语义探针逻辑未增加，后续工具与返工仍由模型自行选择。
- 用等量级的文字替换原“返工才补三段证明”的要求，让首次审查也核实允许的输入、实际路径和具体结果；已有默认值／公共接口测试不必再机械索要调用方证明。

222 项自动化测试通过。新测试覆盖同文件生产者、真实测试调用优先于多行 import、整标识符匹配、注释不触发搜索、新语法片段、返工不重复强制预读。

选 Collective FAQ 验证本文件数据生产者，选 Tracecat 验证测试与间接消费者。模型 `deepseek-v4-flash`；scanner 开启，最多一轮 Lead 自选返工，超时和预算沿用上轮配置。四个完整源码 checkout 共涉及两个仓库，tracked 文件数 71–1971。

FAQ 的首次正确性 Worker 已引用 `_questions` 的真实返回字典代码，并将假设标为 finding，但遗漏了结构化 `findings[]`；协议将其保存为未决，Lead 自选返工后形成了正式 Finding。因此改善来自相关证据到达 Worker，加上可选返工完成输出，不能说首次就完整发布。

Tracecat 现在读到了真实的 `assert list(result) == expected`，不再把测试想象成直接比较 range 和 list。但 Worker 没有继续追踪注册表背后的结果消费者，仍漏掉目标风险。修复版的警告证明了 eager allocation 的行为变化，却把“调用方检查没有在证据中找到”和一个注册表条目，直接写成“无任何限制、不可信输入可达”的 verified 前提；这不够支持已验证的安全 Finding。该同类警告在 v7 的同一修复例已出现，不能因这次也出现就认定为本次检索修改造成的新回归。

原始严格评分：风险 TP=0/2；总 FP=2，其中一个是 FAQ 正确机制但 CWE 分类未匹配，另一个是 Tracecat 修复版警告。目标位置发布从 0/2 到 1/2，不能据此宣称总体准确率明显提高。两个修复版只有一个完全无 Finding。

四例均完成；38 次模型调用、301896 tokens。scanner finding 数和 semantic_probe 调用数在这四例中均为 0。不是靠新增规则或探针救回 FAQ。旧风险例关闭返工，本轮开启可选返工，因此和旧日志的比较不是单变量 A/B，不能把全部提升归因于检索改动。四例中 Lead 都选择了返工；代码不强制每例返工。

## 结论

确定修复了通用取证错误，FAQ 上观察到从风险识别到正式发布的局部改善，但没有达到“两个仓库均稳定改善”的验收。继续残留的是模型把局部证据推广为全路径结论、证据已成立却遗漏 findings[]、CWE 分类不稳定等问题。按本轮范围到此停止，不追加付费复测，不改标签或补 scanner 规则凑成绩。
