# 发布链路审计与六例定向复测

代码版本：`0208e32`。这是一轮已知漏检的定向回归验证，不是新的随机盲测，也不是全量能力证明。没有新增 scanner 规则、仓库特例或探针，没有改 benchmark 标签。

## 已核实的原因

旧全量运行停在 102/200，其中 52 个风险用例。按用例分解：34 个严格命中；18 个严格未命中中，12 个没有 Worker 目标位置候选，4 个有目标位置候选但未发布，2 个已有目标位置结果但严格匹配未通过。目标位置重合不等于语义正确：例如 SymPy 候选的机制仍有争议。因此，不能将所有漏检归咎于发布门禁，也不能根据先前的 3 例推断全量发现能力没有退化。

发布阶段的四个未命中是 Sentry、Newton、SymPy、PyMC。共同现象是 Critic 未完成关键前提核查，而未决状态在代码中直接阻止发布。日志还存在实质推理错误：Newton 的 Critic 将删除的既有回归测试一概视为不独立；Sentry 的 Critic 没有核查实际事件构造和处理路径，就推断缺键事件不可达。SymPy 的候选位置命中，但可能解释了错误的失效机制，不能直接放行。

代码层面的明确问题：

- 全量 runner 默认 `max_revision_rounds=0`，关闭了可选返工；另一处协议兜底又会在有额度时自动返工，形成了“要么禁用，要么隐含强制”的矛盾。
- 合并 scanner 和 Worker 候选后，仅凭证据引用重合，就从发布基线删除 scanner 原始结果。Worker 未决会连带吞掉 scanner 自己的结论。
- Lead 提示词要求独立裁决，但它没有 `read_file`、`search_repository`、`changed_line`、`symbol` 权限；即使选择接受，也没有提交补充证明的正式通道。
- 最终门禁覆盖了前一阶段的验证来源，难以解释“究竟谁验证并发布”。评测又将未最终发布的 scanner 命中算作“发布救回”。对旧 102 例按最终来源重算，目标位置口径的 scanner 救回从 5 降为 3；这不是此次六例的成绩。

## 修复边界

保留 Lead／Worker／Critic 原架构，不增加角色或必经模型轮次。

1. 批量 runner 默认允许最多一轮返工；只有 Lead 显式选择才执行。没有选择时保留未决记录，不自动发起。显式传入 0 仍可做消融对比。
2. scanner 和 Worker 各自接受语义审查，到发布时才合并去重。Worker 不能借 scanner 绕过自身证据要求；scanner 也不会仅因 Worker 未决而消失。针对 scanner 自身结论的、有实际差分依据的反证仍可阻止它发布。scanner 的确定性基线并不意味着静态规则永不误报。
3. 在现有 Lead 最终裁决中开放只读源码工具及可选 `evidence_reviews`。仅对 Critic 未决候选补证：必须引用实际前后代码、给出允许的触发条件和失效链、将每个关键前提绑定到真实成功工具的仓库证据。只有选择索引、置信度或一段解释均不够；已验证反证不能走该通道覆盖。
4. 复用现有证明校验；最终门禁保留 `proof_source` 等验证信息。去掉 Lead 最终输入里重复的整份 Worker 结果，不增加强制工具调用。CWE 不匹配只影响评测分类，不作为发布否决条件。
5. 发布来源统计基于最终实际 finding，不再用中途 verdict 代替发布。报告记录代码内容哈希、返工及 scanner 策略，并拒绝混用不同版本／配置／数据集的缓存。

证明字段校验检查结构、引用和真实差分，不是数学意义的自动语义证明；模型仍可能误读证据。未决候选仍需肯定证据才能发布，不实行“没有反证就全部放行”。

## 冻结版本复测

模型 `deepseek-v4-flash`，目标 `https://api.deepseek.com`；请求超时 60 秒，原有 token/time 配置 64000/120，最多一轮可选返工。这些预算沿用现有按角色分配的实现，不是整个 PR 累计实际输入 token 的硬上限。

六例使用公开 PR 的完整源码 worktree（每个 463–1371 个 tracked 文件），相同数据、标签及模型配置，独立新报告，不复用旧结果。源码校验基于已准备的 base/head 提交。Manim 风险 checkout 的一个无关 `.npz` 图形基准文件已有修改，未动它；评审目标 Python 源码没有本地修改。

| PR | 风险例：目标问题发布 | 严格 TP | 修复版发布数 | 实际发布来源 |
| --- | --- | --- | --- | --- |
| Manim #4704 | 是：不存在的相机属性导致 AttributeError | 0/1 | 0 | Worker → Critic |
| Sentry #4095 | 是：可选 transaction 键被直接下标读取 | 1/1 | 0 | scanner 独立兜底 |
| Newton #3209 | 是：可选稀疏属性的 indexed write 缺少填充 | 1/1 | 0 | Worker → Critic |

Manim 的实际异常机制成立，但模型给出 `CWE-252`，未匹配标注，严格评分保留 FP=1、FN=1。修复版零误报不等于整份严格报告 FP=0。Sentry 的作用域会捕获处理器内部异常，影响是中断该处理器后续的事务元数据补全，不应夸大为整个服务崩溃。

与此前 `current-one-revision-three-miss` 的相同三个风险例相比：严格 TP 从 0/3 到 2/3，目标位置发布从 1/3 到 3/3。风险例模型调用从 30 到 28，实际 token 从 288944 到 239926（约减少 17%）；单次随机运行有波动，不能将全部变化因果归因于某一个修复。与 v7 的严格 2/3 持平。

本次六例合计 51 次模型调用、449897 tokens。实际返工发生 5 次，每次一轮；Sentry 风险例由 Lead 自选不返工，验证了“可选”并非每例强制。全部三个修复版均未发布 finding，但这不足以证明总体误报率为零。

新增的 Lead 补证通道本次没有成功触发：两个风险由 Critic 验证，一个由 scanner 兜底。其正反路径由自动化测试验证，不能宣传成实测救回能力。215 项自动化测试全部通过，覆盖未决不强制返工、引用缺失／失败证据不能发布、有效反证不能覆盖、scanner 独立性与最终去重等。

## 结论与剩余问题

已修复可复现的编排和发布协议缺口，定向正反回归未观察到新增的修复版误报。仍存在 Worker 未发现目标、模型不主动补证、错误解释既有测试、CWE 分类不稳定等问题；并未证明“所有发布失败已根治”或“100 仓库总体表现提升”。建议冻结本轮规则和协议，转向工程性；原 200 例全量运行保持暂停，不自动追加付费测试。
